## 1. Executive conclusions

1. **The task brief's claim is confirmed, not merely "reportedly" true**: `Polymarket/py-clob-client` on GitHub **is archived**. Both a direct GitHub repo fetch and a GitHub search-repositories query independently show `"archived": true` on the repo metadata. Reported archive dates from two separate fetches disagree slightly (**May 11, 2026** vs **May 25, 2026** — see §4.1); the underlying cause is consistent across sources: Polymarket shipped **CLOB V2** (go-live ~April 28, 2026) and the legacy V1-only `py-clob-client` stopped working against it. Polymarket now directs integrators to a **new unified SDK, `Polymarket/py-sdk`** (MIT license, actively developed, 611+ commits, README describes it as covering "public data, authenticated account, trading, builder attribution, and wallet workflows" in one client). A companion repo `Polymarket/py-clob-client-v2` / PyPI `py-clob-client-v2` also exists as a narrower V2-only CLOB client if the full unified SDK is undesired. **Implementation implication: do not build against `py-clob-client`; target `py-sdk` (or `py-clob-client-v2` at minimum) and CLOB V2 endpoints.**
2. Polymarket also archived `Polymarket/agents` (its official AI-agent trading framework) on the **same date pattern (May 11, 2026)**, reinforcing that this was a coordinated V1→V2 SDK deprecation wave, not an isolated repo decision.
3. Independent peer-reviewed-adjacent (SSRN/arXiv-preprint-stage) research from **April–May 2026** supports two claims central to the task brief and worth treating as load-bearing for strategy design:
   - **Simple complement-outcome arbitrage on Polymarket is empirically rare and extremely short-lived** in liquid, high-frequency markets (NBA in-game markets: only 7 executable episodes across 3,042 markets / 173 games, median duration 3.6 seconds, out of 75M+ order-book snapshots examined).
   - **Inferring trade direction (buy vs. sell aggressor) from the public order-book feed alone is unreliable** — one 2026 microstructure study found feed-inferred trade sign matches on-chain ground truth (`OrderFilled` events) only ~59–61.5% of the time, versus ~80% Lee-Ready accuracy benchmarks on traditional equity venues, and that downstream metrics (effective spread, Kyle's lambda) flip sign 43–67% of the time depending on window when built on the unreliable feed-inferred sign. The paper's explicit recommendation is to source trade direction from on-chain `OrderFilled` events, not the WS book feed.
4. Fee structure (V2, effective ~March 30, 2026) is category-dependent taker fees (0.03–0.07 depending on category, some categories fee-free) with **zero maker fees** and a **maker-rebate program** funded by 15–25% of collected taker fees. This materially changes cost modeling versus a flat-fee assumption and should be encoded per-category, not as a single constant.
5. The open-source Polymarket bot ecosystem is large in *count* but thin in *proven quality*: aside from Polymarket's own archived `agents` repo and `warproxxx/poly-maker` (1,453 stars, MIT, actively updated, real market-making logic with inventory skew/regime detection), most arbitrage "scanner" repos surfaced by search are very recently created (2026), have 0–3 stars, and read as scaffolded/AI-assisted projects with untested claims in their own README copy (e.g., "145 tests," "60 passing tests") that could not be independently verified for correctness. Treat these as *pattern references*, not as validated implementations.
6. Academic literature requested in the brief exists and is well-documented (Wolfers & Zitzewitz 2004; Snowberg & Wolfers 2010; Bailey & López de Prado 2014 (Deflated Sharpe Ratio); Bailey, Borwein, López de Prado & Zhu 2015 (PBO/CSCV)) — see the literature table in §3 with citations. A Polymarket-specific microstructure paper (arXiv 2604.24366) and a Polymarket NBA arbitrage paper (arXiv 2605.00864) were both located and are the two most directly relevant primary sources for this project; both were only accessible via WebSearch snippets since arXiv itself was blocked to WebFetch (see limitations, §2).

## 4. Platform-mechanics findings

### 4.1 Official SDK status — CONFIRMED archived

- `github.com/Polymarket/py-clob-client`: **`archived: true`** per both a direct WebFetch of the repo page and a GitHub API search-repositories call. Repo banner text (as fetched): *"This repository has been archived and is no longer maintained. The client is no longer functional and should not be used for new or existing integrations."* README directs migration to `https://github.com/Polymarket/py-sdk`.
- **Date discrepancy noted**: the direct repo-page fetch reported an archive date of **May 25, 2026**; a separate fetch of the related `Polymarket/agents` repo (also archived) stated it was archived **May 11, 2026**, and WebSearch's own synthesis of the py-clob-client query also said "archived by the owner on May 11, 2026." These may reflect a two-stage process (e.g., deprecation notice added ~May 11, formal GitHub archive flag flipped ~May 25) or an inconsistency in one of the two fetches. **Unresolved — do not treat either exact date as certain; both fall within May 2026, consistent with the task brief.**
- Root cause: Polymarket shipped **CLOB V2** with go-live reported around **April 28, 2026**; legacy `py-clob-client` only supports V1 and does not work against production V2.
- Interim/alternative options if the full unified SDK is not desired: **`py-clob-client-v2`** (PyPI: `py-clob-client-v2`; GitHub: `Polymarket/py-clob-client-v2`) — a narrower V2-only CLOB client, versus **`Polymarket/py-sdk`**, the full unified SDK folding Gamma, Data-API, CLOB, and wallet/perps workflows into one package (MIT license, 611+ commits at last check, explicitly marks Perps APIs as "currently experimental").
- **Recommendation for this project**: build against `py-sdk` (preferred, actively maintained, unified surface) or `py-clob-client-v2` at minimum. Any code referencing `py-clob-client` v1 endpoints/signing flow in the existing codebase should be treated as stale and audited.

### 4.2 CLOB API — base URL, auth, order types (B-tier, cross-checked across multiple sources)

- **Auth is two-level**: **L1** = EIP-712 wallet signature (domain `ClobAuthDomain`, version "1", chainId 137/Polygon) used once to derive an API key/secret/passphrase triple; **L2** = HMAC-SHA256 signing of `timestamp_seconds + METHOD + path + body` using the L1-derived secret, applied to every authenticated trading request via five `POLY_*` headers (`POLY_ADDRESS`, `POLY_SIGNATURE`, `POLY_TIMESTAMP`, `POLY_API_KEY`, `POLY_PASSPHRASE`).
- **Order types**: GTC (Good-Till-Cancelled, default resting limit order), GTD (Good-Till-Date, UTC-seconds expiry), FOK (Fill-Or-Kill, fills entirely immediately or cancels — used for market-order-equivalent execution), FAK (Fill-And-Kill, partial immediate fill + cancel remainder). **Post-only** is supported (rejects if it would immediately cross/take, avoiding taker fees). All orders are structurally limit orders; market-like execution is achieved by pricing to cross the spread with FOK/FAK.
- **Batch orders / cancel-all**: search did not surface authoritative, citable documentation text for batch-order or cancel-all endpoint specifics beyond general mentions that such functionality exists in current CLOB tooling (e.g., `polymarket-cli`). **Could not fully verify endpoint-level detail — flagged as unresolved, see §7.** Direct confirmation would require reading `docs.polymarket.com/api-reference` or `/trading/orders/*`, which was blocked in this session.

### 4.3 WebSocket channels (B-tier)

- Endpoints: `wss://ws-subscriptions-clob.polymarket.com/ws/market` (public market data) and `/ws/user` (authenticated order/fill updates); additional `sports` (live game-state) and `rfq` (request-for-quote gateway) channels reported by one source.
- **Heartbeat**: reported as server ping every 5s requiring client pong within 10s, with an additional client-initiated PING every 10s / server PONG pattern described in a different source — these two descriptions are not fully consistent with each other and should be verified against `docs.polymarket.com/market-data/websocket/overview` directly before building a production reconnect/heartbeat handler (that doc page was blocked to WebFetch this session).
- **Snapshot vs incremental**: sources describe the market channel as delivering full order-book state plus incremental price-change/trade/`best_bid_ask`/`market_resolved` events after an initial subscription, but no source gave an authoritative sequence-number field name or reconciliation protocol. **Unresolved — verify directly against primary docs before relying on any assumed sequencing guarantee.**

### 4.4 Fees, minimum order size, tick size (B-tier)

- **Fee Structure V2** (effective ~March 30, 2026): category-dependent **taker** fees — crypto 0.07 (7%), sports 0.03, finance/politics/mentions/tech 0.04, economics/culture/weather/other 0.05; geopolitics/world-events markets reported fee-free. **Maker fees are zero.**
- **Maker rebate program**: 15–25% of collected taker fees redistributed daily to market makers.
- **Tick size / minimum order size**: not confirmed with authoritative figures in this session — search results repeatedly did not surface specific numeric values (candidate figures like "$1.00–$1.75 per 100 shares" appeared in one secondary blog and read as a cost-of-round-trip estimate, not a tick-size spec). **Unresolved, flagged for direct doc verification.**

### 4.5 Negative-risk markets and CTF mechanics (B-tier, consistent across sources)

- **Split**: converts 1 PUSD (collateral) into 1 YES + 1 NO share of a given market; fee-free apart from Polygon gas; executed via the Conditional Token Framework (CTF) contract, gasless when routed through Polymarket's Relayer Client.
- **Merge**: inverse of split — 1 YES + 1 NO → 1 PUSD, only valid pre-resolution.
- **Redeem**: post-resolution only; winning token → $1 PUSD/share, losing token → worthless. Distinct action from merge (merge requires holding both sides pre-resolution; redeem is post-resolution, single-sided).
- **Negative-risk (multi-outcome) markets**: buying YES on one candidate in a NegRisk market is structurally equivalent to buying NO across all other candidates in that market; the `NegRiskAdapter` contract sits atop the CTF and enforces "exactly one outcome wins," and supports one-way conversion of NO tokens into a basket of YES tokens + PUSD pre-resolution for capital efficiency. Reference contract: `Polymarket/neg-risk-ctf-adapter` on GitHub.

### 4.6 Arbitrage viability and trade-direction inference — VERIFIED, matches brief's claims

- Confirmed via arXiv:2605.00864 (WebSearch-snippet tier): single-market complement-outcome arbitrage in liquid NBA markets is empirically rare and short-lived (7 executable episodes across 3,042 markets, median 3.6 seconds, from 75M+ LOB snapshots across 173 games). A second, less formally sourced blog-style figure claimed average arbitrage-window duration fell from 12.3s (2024) to 2.7s (2026) with 73% of profits captured by sub-100ms bots — **this specific figure is C-tier (SEO/blog content), unconfirmed against a primary source, and should not be treated as reliable as the arXiv paper's numbers.**
- Confirmed via arXiv:2604.24366 (WebSearch-snippet tier): public order-book-feed-inferred trade direction agrees with on-chain `OrderFilled`-event ground truth only ~59–61.5% of the time (vs. ~80% Lee-Ready benchmark on Nasdaq), and derived microstructure metrics (effective spread, Kyle's lambda) are unstable/sign-flipping when built on the unreliable feed-inferred direction. Recommendation: any direction-dependent signal in this project's codebase should be built from on-chain `OrderFilled` event logs (CTF Exchange V1 contract logs ~255M such events per one source), not from the WS `market` channel's implied trade sign.

## 6. Strategy implications

- **SDK migration is mandatory, not optional.** Any code path in this repo built against `py-clob-client` v1 will not function against current production CLOB V2. Prioritize an audit of existing integration code against this finding.
- **Do not build a "complement-sum < $1" arbitrage strategy as a primary alpha source.** The most relevant primary research (arXiv:2605.00864) found such opportunities empirically rare and typically sub-4-second in duration even in Polymarket's most liquid sports markets — a retail-latency bot is very unlikely to capture them reliably. If pursued at all, it should be a low-priority/opportunistic module, sized and gated by depth-walked, fee-and-gas-aware thresholds (the pattern several scanner repos already implement), not a headline strategy.
- **Any signal derived from "who is buying/selling" via the public order-book feed should be treated as noisy (~59–61% directional accuracy per arXiv:2604.24366) unless corroborated by on-chain `OrderFilled` event data.** If the project's edge depends on order-flow/toxicity signals (e.g., the kind `poly-maker` uses), source direction from chain events, not WS-feed-inferred sign.
- **Fee modeling must be category-aware**, not a flat constant — taker fees range roughly 0–7% by category under Fee Structure V2, and maker rebates (15–25% of taker fees collected) are a real, quantifiable revenue stream for resting-order strategies.
- **Backtest validation should incorporate Deflated Sharpe Ratio and PBO/CSCV methodology** (Bailey & López de Prado; Bailey, Borwein, López de Prado & Zhu) given this is exactly the kind of small-sample, many-parameter-search context those papers were written to guard against. Purged/embargoed CV (López de Prado) should be adapted for any ML-labeled, event-driven Polymarket dataset to avoid look-ahead leakage across overlapping event windows.
- **Kelly/fractional-Kelly sizing is directly applicable** given Polymarket payoffs are bounded both above and below (unlike typical unbounded financial instruments) — half-Kelly is the commonly cited practical default in the sourced material, trading ~25% of full-Kelly growth for materially reduced drawdown/variance.
